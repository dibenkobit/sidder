---
title: What is sidder?
description: An ordered, resumable and transparent seed runner for Postgres.
---

Migrations have discovery, an inferred order, a record of what ran, a status command and
one entry point. Seeds usually have a folder of scripts and an `&&` chain someone maintains
by hand.

sidder gives seeds the runner migrations have had for years:

- discover seed files by convention;
- order them from real dependencies;
- record successful runs in the database;
- keep the journal write in the same transaction as the seed;
- show what ran, what skipped and why;
- prevent concurrent deploys from applying a seed twice.

<Callout title="The design rule" type="idea">
  **Guessing is fine. Guessing quietly is not.** sidder names the config, environment,
  seed names and order it inferred before anything reaches the database.
</Callout>

## The smallest useful surface

There are three things to learn:

1. the config;
2. `defineSeed`;
3. the `db` handle a seed receives.

Everything else is optional. There is no factory DSL, global registry or special query API.
Your existing database code stays ordinary database code.

```ts title="seeds/roles.mts"
import { defineSeed } from 'sidder';

export default defineSeed({
  async run({ db }) {
    await db.query("insert into roles (name) values ('admin')");
  },
});
```
